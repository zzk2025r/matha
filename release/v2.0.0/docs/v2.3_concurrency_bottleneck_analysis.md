## 1000 线程下的潜在瓶颈

### 瓶颈 1：RLock 序列化竞争（中等风险）

**位置**：`RecoveryStrategy._lock`

```python
with cls._lock:
    strategies = list(cls._strategies.get(error.stage, []))
```

**问题**：1000 线程同时调用 `try_recover()`，全部串行获取同一把 RLock。
虽然持有时间短（仅复制列表），但 1000 线程的抢锁开销会累积。

**数据估算**：
- 每次锁持有 ~1μs（列表拷贝）
- 1000 线程串行等待 ≈ 1000 × 1μs = 1ms
- 实际测试：480ms（主要瓶颈在策略函数执行，不在锁本身）

**预优化方案**：

```python
# 方案 A：读写锁分离（推荐）
import threading
from contextlib import contextmanager

class RecoveryStrategy:
    _read_lock = threading.RLock()
    _write_lock = threading.Lock()  # 独立的写锁

    @classmethod
    def register(cls, stage):
        def decorator(fn):
            with cls._write_lock:     # 写锁（低频）
                if stage not in cls._strategies:
                    cls._strategies[stage] = []
                cls._strategies[stage].append(fn)
            return fn
        return decorator

    @classmethod
    def try_recover(cls, error):
        with cls._read_lock:          # 读锁（高频，不阻塞其他读）
            strategies = list(cls._strategies.get(error.stage, []))
        # 锁外执行策略函数
        for strategy in strategies:
            try:
                result = strategy(error)
                if result is not None:
                    return result
            except Exception:
                continue
        return None
```

### 瓶颈 2：Python GIL 限制（固有限制）

**问题**：CPython 的 GIL 使得同一时刻只有一个线程执行 Python 字节码。
1000 个线程并发时，大部分时间花在 GIL 争抢而非真正并行。

**数据**：
- 解析 CPU 密集型操作（正则匹配）：GIL 下串行，无法加速
- 策略函数执行：GIL 下串行

**预优化方案**：

```python
# 方案 B：ThreadPoolExecutor 替代原生线程
from concurrent.futures import ThreadPoolExecutor, as_completed

def parse_batch_sequential(cases, max_workers=50):
    """限制并发度，避免线程爆炸。"""
    results = []
    with ThreadPoolExecutor(max_workers=max_workers) as executor:
        futures = {executor.submit(parser.parse, case): case for case in cases}
        for future in as_completed(futures):
            results.append(future.result())
    return results

# 方案 C：进程池绕过 GIL（CPU 密集型场景）
from concurrent.futures import ProcessPoolExecutor

def parse_with_processes(cases, max_workers=8):
    """用进程池绕过 GIL，适合 CPU 密集型解析。"""
    with ProcessPoolExecutor(max_workers=max_workers) as executor:
        return list(executor.map(parser.parse, cases))
```

### 瓶颈 3：REPLState.error_log 列表拷贝开销（低风险）

**问题**：`get_error_log()` 每次都拷贝整个列表，1000 线程 × 10000 条错误 = 大量内存分配。

**数据**：
- 100 线程 × 10 错误/线程 = 1000 条，拷贝开销可忽略
- 1000 线程 × 10 错误/线程 = 10000 条，拷贝 ~80KB，仍可接受

**预优化方案**：

```python
# 方案 D：使用 collections.deque + 快照
from collections import deque

class REPLState:
    def __init__(self):
        self._error_log: deque[MathaError] = deque(maxlen=10000)
        self._error_lock = threading.RLock()

    def append_error(self, error: MathaError) -> None:
        with self._error_lock:
            self._error_log.append(error)

    def get_error_log(self) -> list[MathaError]:
        with self._error_lock:
            return list(self._error_log)  # deque 转 list，O(n)

# 方案 E：Copy-on-Write（极端高性能场景）
import copy
class REPLState:
    def __init__(self):
        self._errors: list[MathaError] = []
        self._lock = threading.RLock()
        self._snapshot_version = 0

    def append_error(self, error: MathaError) -> None:
        with self._lock:
            self._errors.append(error)
            self._snapshot_version += 1

    def get_snapshot(self) -> tuple[list, int]:
        """返回当前快照，避免全量拷贝。"""
        with self._lock:
            return (list(self._errors), self._snapshot_version)
```

### 瓶颈 4：意图解析器实例重复创建（中风险）

**问题**：当前每个线程创建独立的 `EnhancedIntentParser()` 实例，
导致 `IntentClassifier`、`ParamExtractor`、`CodeGenerator` 实例重复。

**数据**：
- 每个实例 ~1KB 内存
- 1000 线程 = 3KB 额外内存（可忽略）
- 但频繁创建/销毁会有 GC 压力

**预优化方案**：

```python
# 方案 F：线程局部缓存（ThreadLocal）
import threading

_thread_local = threading.local()

def get_parser() -> EnhancedIntentParser:
    """获取当前线程的解析器实例（缓存）。"""
    if not hasattr(_thread_local, 'parser'):
        _thread_local.parser = EnhancedIntentParser()
    return _thread_local.parser

# 使用
parser = get_parser()
result = parser.parse(text)
```

## 优先级排序

| 优先级 | 瓶颈 | 风险 | 影响 | 建议 |
|---|---|---|---|---|
| P0 | Python GIL | 🟡 中 | CPU 密集解析无法并行 | 进程池（方案 C） |
| P1 | RLock 串行竞争 | 🟡 中 | 1000+ 线程延迟增加 | 读写锁分离（方案 A） |
| P2 | error_log 拷贝 | 🟢 低 | 高错误场景内存压力 | Copy-on-Write（方案 E） |
| P3 | 实例重复创建 | 🟢 低 | GC 压力 | ThreadLocal 缓存（方案 F） |

---

## 结论

当前 1000 线程下 **零异常**，RLock 机制工作正常。
主要瓶颈是 **Python GIL**（语言层面限制），而非代码设计问题。
对于 REPL 场景（单线程交互），当前实现已完全足够。
若未来需要真正的并发解析服务，建议实施 P0 方案（进程池）。
