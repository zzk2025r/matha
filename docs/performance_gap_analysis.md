## 性能差距根因分析

### 1. 解释器开销（主要因素）

```
Matha 执行流程:
  源代码 → Lexer → Parser → AST → Interpreter → 结果
  每次调用: ~1-5μs 固定开销（与计算量无关）

Rust 执行流程:
  源代码 → rustc -O → 原生机器码 → 结果
  每次调用: ~5-50ns（无解释器开销）
```

**影响**：
- 简单表达式（多项式求值）：解释器开销占比 80%+
- 复杂计算（矩阵乘法）：计算本身占主导，差距缩小
- 递归算法（斐波那契）：解释器开销被指数放大

### 2. 内存模型差异

| 特性 | Python (Matha) | Rust |
|------|---------------|------|
| 整数 | 对象头 + 引用计数 | 直接值 (i64) |
| 浮点数 | PyFloat 对象 | 直接值 (f64) |
| 列表 | 堆分配 + 指针数组 | 连续内存 (Vec) |
| 内存布局 | 离散分配 | 连续分配 (缓存友好) |

**影响**：
- 矩阵乘法：Python 的 `a[i][k]` 每次解引用需 2 次指针跳转
- Rust 的 `a[i*size+k]` 是单条 SIMD 指令

### 3. 类型系统影响

```python
# Matha (Python) — 运行时类型分发
x = some_number  # 每次需检查类型
result = x + y   # 需查表分派到 add_int / add_float / ...

# Rust — 编译期单态化
let x: f64 = 2.5;  // 编译期确定类型
let result = x + y; // 直接 emit fadd 指令，无分派开销
```

### 4. 递归 vs 迭代

```
斐波那契 F(30) 的递归调用次数: 2,692,537 次

Matha (递归解释执行):
  每次调用 = 函数查表 + 栈帧分配 + 参数检查 + 返回
  总开销 ≈ 2.7M × 1μs = 2690ms (理论)
  实际: 269ms (C 解释器优化)

Rust (迭代 + 编译优化):
  每次循环 = 1 条加法指令
  总开销 ≈ 30 × 5ns = 150ns
  实际: ~0.5ms (含循环开销)
```
